C4 model · Simon Brown 2022

Appwrite Boundary Blueprints

Four drawings of the Appwrite boundary in the VIEWS platform, in Brown's vocabulary: system context, containers, and one container's components as built today beside the same container once the gateway exists. Facts in the drawings were checked in the code on 2026‑11‑27; anything taken from a document rather than the code is marked.

One rule from the book decides how the gateway is drawn. Brown, §4.2: “a container refers to an execution context… libraries or modules should not be considered as containers unless they are runnable on their own.” So the form of the gateway changes what kind of box it gets. As an installable package it is a component — “a grouping of related functionality encapsulated behind a well-defined interface” — repeated inside three containers. As a program on Hetzner, called over HTTP, it is a container of its own, and it appears once. The operator decided the program form on 2026‑11‑21, so diagram 5 is the target and diagram 4 is the other form, drawn for comparison rather than as a proposal.

The second thing the target changes is bigger than the gateway. The forecasts leave Appwrite. A prediction store on Hetzner replaces both views-forecasts and the production_forecasts bucket; Appwrite keeps only the per-audience delivery buckets — the credentialed door partners pull from. Diagrams 1 to 4 are therefore drawings of today, kept because the migration has to start from them.

§4.7 settles the second question: a vendor SDK is “really just a technology choice that components make use of… implementation detail rather than a component in its own right.” So the Appwrite SDK is drawn as a technology label on the component that uses it, never as a box of its own.
